# LayerBase Sync / Async ECS 基准测试设计方案

## 0. 基准测试目标

这组 benchmark 不是为了证明：

```text
Async 一定比 Sync 快。
```

而是为了证明：

```text
1. Sync 模式的 ECS 执行成本是多少。
2. Async 模式的主线程提交成本是多少。
3. Async 模式的 Worker 执行成本是多少。
4. Async 模式结果回流到主线程的 Drain 成本是多少。
5. 在多少实体数量 / 多少计算强度下，Async 值得使用。
```

最终要回答的问题是：

```text
轻量 Query：
  Sync 是否更合适？

中/重 Query：
  Async 能否显著降低主线程帧内耗时？

Bring Query：
  ECS -> ActorEvent 的异步回流成本是否可控？

真实帧循环：
  Async 是否降低主线程 p95 帧耗时？
```

---

# 1. 不要只测 Total Time

如果你这样测：

```text
Async 提交 Query
等待 EcsWorker 完成
Drain 结果
```

然后和 Sync 直接执行比，Async 很可能更慢。

因为 Async 多了：

```text
WorkItem 打包
MPSC 入队
线程唤醒
EcsWorker 出队
Result 入队
主线程 Drain
```

所以 Async 的真正收益不在“单个 Query 总时间更短”，而在：

```text
主线程不用阻塞执行 ECS。
ECS 可以和主线程其他工作并行。
```

因此必须拆指标。

---

# 2. 核心指标

## 2.1 SyncExecTime

同步 Query 的执行耗时。

```text
SyncExecTime =
  主线程直接执行 Query.ForEach 的耗时
```

它回答：

```text
如果不异步，这个 ECS 任务会占用主线程多久？
```

---

## 2.2 AsyncSubmitTime

异步 Query 的提交耗时。

```text
AsyncSubmitTime =
  构造 WorkItem
  MPSC.Enqueue
  Signal Worker
```

它回答：

```text
异步模式下，主线程为了提交这个 ECS 任务付出了多少成本？
```

理想情况：

```text
AsyncSubmitTime 远小于 SyncExecTime。
```

---

## 2.3 AsyncWorkerExecTime

EcsWorker 实际执行 Query 的耗时。

```text
AsyncWorkerExecTime =
  EcsWorker 出队后执行 ECS Query 的时间
```

它回答：

```text
同样的 ECS 任务，放到 Worker 后执行本身有没有额外损失？
```

---

## 2.4 AsyncDrainTime

主线程 Drain ECS 结果的耗时。

```text
AsyncDrainTime =
  EcsResultQueue.Drain
  ActorEventCommandBuffer.Flush
  Post 到 ActorWorld / ActorScheduler
```

普通 Query 可能没有 Drain 成本。

Bring Query 会有明显 Drain 成本。

---

## 2.5 MainThreadCost

这是最重要的指标。

```text
SyncMainThreadCost =
  SyncExecTime

AsyncMainThreadCost =
  AsyncSubmitTime + AsyncDrainTime
```

Async 是否值得用，主要看：

```text
AsyncMainThreadCost 是否显著低于 SyncMainThreadCost。
```

---

## 2.6 EndToEndLatency

异步结果从提交到主线程可见的耗时。

```text
EndToEndLatency =
  SubmitTime -> ResultVisibleTime
```

它回答：

```text
异步模式带来了多少结果延迟？
是同帧末尾可见？
下一帧可见？
还是多帧后才可见？
```

---

## 2.7 AllocatedBytes

异步模式容易因为 WorkItem、Result、CommandBuffer 产生 GC。

必须测：

```text
AllocatedBytes / Operation
```

第一版可以允许少量分配，但要知道它在哪里。

后续优化目标是：

```text
WorkItem 池化
ActorEventCommandBuffer 池化
Typed Batch 池化
```

# 4. Benchmark 组一：纯 Query 基准

## 4.1 测试目标

验证普通 Query 在 Sync / Async 下的基础差异。

测试对象：

```text
Position += Velocity
```

组件：

```csharp
public struct BenchPosition : IComponent
{
    public float X;
    public float Y;
}

public struct BenchVelocity : IComponent
{
    public float X;
    public float Y;
}
```

Job：

```csharp
public readonly struct MoveJob :
    IQueryJob<BenchPosition, BenchVelocity>
{
    public void Execute(
        Entity entity,
        ref BenchPosition position,
        ref BenchVelocity velocity)
    {
        position.X += velocity.X;
        position.Y += velocity.Y;
    }
}
```

---

## 4.2 参数设计

```csharp
[Params(1_000, 10_000, 100_000)]
public int EntityCount;
```

如果只测轻量计算，Async 大概率吃亏。

所以还要加计算强度：

```csharp
[Params(0, 16, 128, 512)]
public int WorkIterations;
```

扩展 Job：

```csharp
public readonly struct MoveWithWorkJob :
    IQueryJob<BenchPosition, BenchVelocity>
{
    private readonly int _iterations;

    public MoveWithWorkJob(int iterations)
    {
        _iterations = iterations;
    }

    public void Execute(
        Entity entity,
        ref BenchPosition position,
        ref BenchVelocity velocity)
    {
        float x = position.X;
        float y = position.Y;

        for (int i = 0; i < _iterations; i++)
        {
            x = x * 1.0001f + velocity.X;
            y = y * 0.9999f + velocity.Y;
        }

        position.X = x;
        position.Y = y;
    }
}
```

---

## 4.3 Benchmark 方法

```csharp
[Benchmark(Baseline = true)]
public void Sync_PlainQuery_Execute()
{
    var job = new MoveWithWorkJob(WorkIterations);

    _syncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity>()
        .ForEach(ref job);
}
```

```csharp
[Benchmark]
public void Async_PlainQuery_SubmitOnly()
{
    var job = new MoveWithWorkJob(WorkIterations);

    _asyncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity>()
        .ForEach(ref job);
}
```

```csharp
[Benchmark]
public void Async_PlainQuery_EndToEnd()
{
    var job = new MoveWithWorkJob(WorkIterations);

    EcsFence fence = _asyncRuntime.EcsScheduler.CurrentFenceForTest;

    _asyncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity>()
        .ForEach(ref job);

    _asyncRuntime.EcsScheduler.WaitFenceForTest(fence.Next());
}
```

---

## 4.4 预期结果解释

轻量任务：

```text
EntityCount = 1_000
WorkIterations = 0

Sync 可能更快。
Async 总耗时可能更慢。
这是正常的。
```

重任务：

```text
EntityCount = 100_000
WorkIterations = 128 / 512

AsyncSubmitTime 应该远小于 SyncExecTime。
AsyncEndToEnd 可能略高于 SyncExecTime。
但主线程占用显著下降。
```

# 5. Benchmark 组二：Async 主线程释放量

## 5.1 测试目标

这个 benchmark 要回答：

```text
Async 到底释放了多少主线程时间？
```

核心计算：

```text
FreedMainThreadTime =
  SyncExecTime - AsyncSubmitTime
```

如果是 Bring Query：

```text
FreedMainThreadTime =
  SyncExecTime - (AsyncSubmitTime + AsyncDrainTime)
```

---

## 5.2 结果标准

建议报告里明确输出：

```text
EntityCount
WorkIterations
SyncExecTime
AsyncSubmitTime
AsyncEndToEndTime
MainThreadSavedRatio
```

其中：

```text
MainThreadSavedRatio =
  1 - AsyncSubmitTime / SyncExecTime
```

例如：

```text
SyncExecTime = 2.0 ms
AsyncSubmitTime = 0.05 ms

MainThreadSavedRatio = 97.5%
```

这才是 Async 的核心价值。

# 6. Benchmark 组三：Bring Query 基准

## 6.1 测试目标

Bring Query 比普通 Query 多了：

```text
ProjectedActorRef
ProjectResult
ActorEvent 生成
ActorEventCommandBuffer
主线程 Flush
ActorBehaviour 处理
```

所以要单独测。

---

## 6.2 组件和事件

```csharp
public struct BenchAoi : IComponent
{
    public bool Visible;
}

public struct BenchMoveViewEvent : IActorEvent
{
    public float X;
    public float Y;

    public BenchMoveViewEvent(float x, float y)
    {
        X = x;
        Y = y;
    }
}
```

Job：

```csharp
public readonly struct MoveViewJob :
    IProjectionJob3x1<
        BenchPosition,
        BenchVelocity,
        BenchAoi,
        BenchMoveViewEvent>
{
    private readonly int _iterations;

    public MoveViewJob(int iterations)
    {
        _iterations = iterations;
    }

    public ProjectResult Execute(
        Entity entity,
        ref BenchPosition position,
        ref BenchVelocity velocity,
        ref BenchAoi aoi,
        ref BenchMoveViewEvent view)
    {
        if (!aoi.Visible)
        {
            return ProjectResult.Fail;
        }

        float x = position.X;
        float y = position.Y;

        for (int i = 0; i < _iterations; i++)
        {
            x = x * 1.0001f + velocity.X;
            y = y * 0.9999f + velocity.Y;
        }

        position.X = x;
        position.Y = y;

        view = new BenchMoveViewEvent(x, y);

        return ProjectResult.Success;
    }
}
```

---

## 6.3 Benchmark 方法

```csharp
[Benchmark(Baseline = true)]
public void Sync_BringQuery_ExecuteAndPost()
{
    var job = new MoveViewJob(WorkIterations);

    _syncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity, BenchAoi>()
        .Bring<BenchMoveViewEvent>()
        .ForEach(ref job)
        .Batch()
        .Post();

    _syncRuntime.Pump(0.016f);
}
```

```csharp
[Benchmark]
public void Async_BringQuery_SubmitOnly()
{
    var job = new MoveViewJob(WorkIterations);

    _asyncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity, BenchAoi>()
        .Bring<BenchMoveViewEvent>()
        .ForEach(ref job)
        .Batch()
        .Post();
}
```

```csharp
[Benchmark]
public void Async_BringQuery_EndToEnd()
{
    var job = new MoveViewJob(WorkIterations);

    EcsFence fence = _asyncRuntime.EcsScheduler.CurrentFenceForTest;

    _asyncRuntime.EcsWorld
        .Query<BenchPosition, BenchVelocity, BenchAoi>()
        .Bring<BenchMoveViewEvent>()
        .ForEach(ref job)
        .Batch()
        .Post();

    _asyncRuntime.EcsScheduler.WaitFenceForTest(fence.Next());

    _asyncRuntime.Pump(0.016f);
}
```

---

## 6.4 需要单独测 Flush

```csharp
[Benchmark]
public void Async_BringQuery_DrainResultsOnly()
{
    _asyncRuntime.EcsScheduler.DrainResults(int.MaxValue);
}
```

不过这个方法需要预先准备好 result queue，否则 benchmark 会测到空 drain。

更好的做法是：

```text
GlobalSetup:
  先提交一批 Bring Query
  WaitFence
Benchmark:
  只测 DrainResults
```

# 7. Benchmark 组四：真实帧循环模拟

## 7.1 为什么需要这个？

纯 BenchmarkDotNet 方法常常会变成：

```text
提交异步任务
立刻等待它完成
```

这会抹掉 Async 的优势。

真正游戏里是：

```text
主线程提交 ECS 任务
主线程继续处理 Post / Actor / 输入 / 表现
EcsWorker 同时计算 ECS
下一帧或本帧末尾回流结果
```

所以需要 Frame Simulation Benchmark。

---

## 7.2 模拟帧循环

```csharp
[Benchmark]
public void Sync_FrameLoop()
{
    for (int frame = 0; frame < FrameCount; frame++)
    {
        var job = new MoveWithWorkJob(WorkIterations);

        _syncRuntime.EcsWorld
            .Query<BenchPosition, BenchVelocity>()
            .ForEach(ref job);

        SimulateMainThreadWork();

        _syncRuntime.Pump(0.016f);
    }
}
```

```csharp
[Benchmark]
public void Async_FrameLoop()
{
    for (int frame = 0; frame < FrameCount; frame++)
    {
        var job = new MoveWithWorkJob(WorkIterations);

        _asyncRuntime.EcsWorld
            .Query<BenchPosition, BenchVelocity>()
            .ForEach(ref job);

        SimulateMainThreadWork();

        _asyncRuntime.Pump(0.016f);
    }

    _asyncRuntime.EcsScheduler.WaitIdleForTest();
}
```

`SimulateMainThreadWork`：

```csharp
private static void SimulateMainThreadWork()
{
    float x = 1f;

    for (int i = 0; i < MainThreadWorkIterations; i++)
    {
        x = x * 1.00001f + 0.1f;
    }

    _sink = x;
}
```

---

## 7.3 Frame Benchmark 要记录什么？

BenchmarkDotNet 给的是总时间，但你还应该内部记录：

```text
每帧主线程耗时
p50
p95
p99
最大帧耗时
平均结果延迟帧数
```

建议做一个非 BenchmarkDotNet 的 profiler-style test：

```csharp
[Test]
public void AsyncFrameLoop_ReducesMainThreadP95()
{
    FrameProfile sync = RunSyncFrameProfile();
    FrameProfile async = RunAsyncFrameProfile();

    TestContext.WriteLine(sync);
    TestContext.WriteLine(async);

    Assert.That(async.MainThreadP95, Is.LessThan(sync.MainThreadP95));
}
```

这个测试可以不作为硬性单元测试，只作为性能报告输出。

# 8. Benchmark 组五：拐点测试

## 8.1 目的

你需要知道：

```text
多少实体数量以下，Sync 更好？
多少实体数量以上，Async 更好？
多少计算强度以上，Async 值得用？
```

这叫 break-even point。

---

## 8.2 参数矩阵

建议：

```csharp
[Params(100, 1_000, 10_000, 100_000)]
public int EntityCount;

[Params(0, 8, 32, 128, 512)]
public int WorkIterations;
```

最终结果会出现这样的规律：

```text
100 entities + 0 work:
  Sync 最优。

1_000 entities + 0 work:
  Sync 大概率仍最优。

10_000 entities + 32 work:
  Async 开始释放明显主线程时间。

100_000 entities + 128 work:
  Async 主线程收益非常明显。
```

你真正想找的是：

```text
Async 值得开启的拐点。
```

# 9. 验收标准建议

不要定死“Async 必须总耗时更短”。

建议定这些标准。

## 9.1 默认 Sync 性能不退化

```text
Sync_PlainQuery_Execute
```

和当前 benchmark 对比：

```text
不能因为新增 Scheduler 壳导致明显退化。
```

建议标准：

```text
Sync 模式回归不超过 3% - 5%。
```

---

## 9.2 Async Submit 成本足够低

对于 10k / 100k 实体：

```text
AsyncSubmitTime 应该接近常数级。
```

理想情况：

```text
AsyncSubmitTime 不随 EntityCount 线性增长。
```

如果 Submit 成本随实体数增长，说明你在主线程提前做了太多 Query 构建/扫描。

---

## 9.3 Async 主线程占用显著下降

中/重负载下：

```text
AsyncMainThreadCost < SyncMainThreadCost * 0.2
```

也就是：

```text
异步主线程成本低于同步的 20%
```

这个标准比“总耗时更快”更有意义。

---

## 9.4 EndToEnd 延迟可控

目标：

```text
普通 Query：
  Worker 完成后 ECS 数据可见。

Bring Query：
  Worker 完成后，下一次 Runtime.Pump 可投递给 Actor。
```

可以记录：

```text
ResultDelayFrames <= 1 或 <= 2
```

看你最终 Pump 阶段怎么设计。

---

## 9.5 GC 分配可控

第一版可以允许：

```text
每个异步 Query 一个 WorkItem 分配
每个 Bring Result 一个 CommandBuffer 分配
```

但要记录。

长期目标：

```text
AsyncSubmit allocated bytes 接近 0
AsyncBring allocated bytes 可通过池化下降
```

---

# 10. 不同 benchmark 的解释口径

## 10.1 如果 Sync 比 Async EndToEnd 快

这是正常的。

说明：

```text
单任务纯总耗时下，Async 有跨线程成本。
```

不是失败。

---

## 10.2 如果 Async SubmitOnly 很低

这是成功信号。

说明：

```text
主线程可以快速把 ECS 工作移出去。
```

---

## 10.3 如果 Async FrameLoop p95 更低

这是最重要的成功信号。

说明：

```text
异步 ECS 真的降低了主线程帧压力。
```

---

## 10.4 如果 Async Light Query 表现很差

这也是合理的。

结论应该是：

```text
轻量 Query 不建议异步化，或者统一异步模式下需要批处理多个轻量 Query。
```

建议最终有这些方法：

```text
EcsExecutionModeBenchmarks

Plain Query:
  Sync_PlainQuery_Execute
  Async_PlainQuery_SubmitOnly
  Async_PlainQuery_EndToEnd

Bring Query:
  Sync_BringQuery_ExecuteAndPost
  Async_BringQuery_SubmitOnly
  Async_BringQuery_EndToEnd
  Async_BringQuery_DrainOnly

  Sync_FrameLoop
  Async_FrameLoop

Break-even:
  EntityCount: 100 / 1k / 10k / 100k
  WorkIterations: 0 / 8 / 32 / 128 / 512
```

# 12. 最终结论

你应该用三套标准证明 Sync / Async 的区别：

```text
1. 总耗时标准：
   Sync 通常更适合轻量任务。

2. 主线程占用标准：
   Async 在中/重任务下应该明显降低主线程耗时。

3. 帧循环标准：
   Async 应该降低真实帧循环中的 p95 / p99 主线程耗时。
```

最重要的不是证明：

```text
Async EndToEnd 一定比 Sync 快。
```

而是证明：

```text
Async 把 ECS 工作从主线程搬走后，主线程帧预算变得更安全。
```

所以最终报告应该长这样：

```text
Sync 模式：
  总耗时低，轻量任务更合适。
  但 ECS 工作全部占用主线程。

Async 模式：
  单任务 EndToEnd 有额外成本。
  但 Submit 成本低，主线程被释放。
  在中/重 ECS 负载下能明显降低主线程 p95 帧耗时。
```
